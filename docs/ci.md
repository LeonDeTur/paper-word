# CI и автоматические релизы

## Проверки

`CI` запускается для PR в `main`, вручную через Actions и как переиспользуемый workflow из `Release` при push в `main`.

1. **Quality (Ubuntu/Windows)**: Node из `.node-version`, установка по lockfile, Conventional Commits и имена веток, согласованность версий, приватные файлы, Prettier, Oxlint, TypeScript/Vite/esbuild, unit- и tooling-тесты.
2. **Integration (Ubuntu/Windows)**: API/SQLite/OAuth, удалённый MCP через официальный клиент, stdio, ограничения разрешений и миграции. На Linux дополнительно формируется LCOV.
3. **Browser and accessibility**: установленный Chromium, экран компьютера и телефона, OAuth, чтение и карточки, Axe. HTML/JUnit/trace/снимки доступны в артефактах Actions 14 дней.
4. **Docker build and smoke test**: Linux-образ собирается без отправки в registry, запускается с фиктивным паролем; проверяются production-конфигурация, отказ без входа и работа от непривилегированного пользователя. Личные данные в образ не копируются.
5. **CI passed**: общий обязательный результат, успешный только после всех четырёх групп.

Отдельный `Security` запускает CodeQL и `npm audit --audit-level=high` на PR, push в `main` и раз в неделю. Dependabot предлагает обновления npm и Actions; автоматического слияния зависимостей нет.

Actions закреплены на полные SHA. Обычные проверки имеют только `contents: read`, checkout не сохраняет credentials. Код PR не выполняется через `pull_request_target`. Только release-job после успешного CI в `main` получает права на создание PR/релизов и запуск CI для ветки бота. Секреты модели и доступ к VPS в Actions не нужны. Self-hosted runner на сервере с VPN не требуется.

## Release PR

После успешных проверок `main` бот определяет, был ли слит новый номер версии. Обычные изменения подготавливают или обновляют PR из `chore/release`:

- Conventional Commits определяют следующий SemVer;
- обновляются `package.json`, обе записи версии в `package-lock.json` и `CHANGELOG.md`;
- существующие ручные заметки `Unreleased` переносятся в новый раздел;
- PR получает заголовок `chore(release): vX.Y.Z` и описание изменений;
- CI для ветки бота запускается явно через `workflow_dispatch`, поэтому личный PAT не требуется.

До слияния PR ни тег, ни публичный релиз не создаются. После слияния снова выполняется полный CI. Затем публикуется GitHub Release **для проверенного SHA**: версия, автоматически собранные примечания, архив приложения и `SHA256SUMS`. Сначала используется черновик; при сбое можно повторить workflow. Уже опубликованные assets не перезаписываются, а существующий тег не переносится на другой коммит.

Архив содержит только `build`, `dist`, package-файлы, лицензию, публичные примеры и документацию. Для запуска распаковать, установить Node нужной версии, выполнить `npm ci --omit=dev`, настроить окружение и `npm start`. В архив не входят `node_modules`, личная библиотека, `.env`, токены и исходные статьи. Это переносимый runtime-архив; для сборки Docker или разработки нужен исходный Git-репозиторий.

Нет публикации в npm, отправки образа в registry или автоматического развёртывания на VPS. Это можно подключить отдельно после проверки первого релиза.

## Настройки GitHub

Нужен публичный репозиторий с Actions. В **Settings → Actions → General** разрешите GitHub Actions создавать pull requests. Default token permissions можно оставить read-only: release-job повышает права только для своей работы. Для CodeQL нужен включённый code scanning; для защиты от утечек рекомендуется GitHub secret scanning и push protection.

Первый базовый тег `v0.2.0` должен быть в origin. Перед первой настройкой проверьте `git show v0.2.0` и отправьте существующий проверенный тег командой `git push origin v0.2.0`. Не переносите его на другой коммит. Последующие теги создаёт workflow.

Рекомендуемая защита `main`: изменения через PR, обязательные **CI passed**, **CodeQL**, **Dependency audit**, закрытые обсуждения и запрет force-push. Для личного проекта не требуйте независимого approving review, если второго сопровождающего нет. Автоматизация не включает такую политику без отдельного решения владельца.

Если первый Release PR не создаётся, проверьте разрешение на создание PR, наличие исходного тега и вкладку Actions → Release. Для ручного повторения выбирайте `main`. Не запускайте публикацию от непроверенного SHA. При изменении workflow сначала проверьте его в PR.
