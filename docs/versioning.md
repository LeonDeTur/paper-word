# Версии и Git

Единый источник версии — `package.json`. HTTP `/api/config`, MCP и настройки показывают ту же версию. Первый релиз — `0.2.0`, тег `v0.2.0`. Версия схемы SQLite — отдельное число `PRAGMA user_version` (сейчас 3); приложение отказывается открывать более новую схему.

Ветки: `feat/название`, `fix/название`, `docs/название`, `chore/название`. Коммиты: `feat: …`, `fix: …`, `docs: …`, `chore(release): …`. Префикс `codex/` не используется.

SemVer: PATCH — исправления; MINOR — совместимые возможности; MAJOR — несовместимый контракт. В период `0.x` несовместимые изменения требуют новой MINOR и явного описания в журнале.

Для следующего релиза:

1. Заполнить датированный раздел `CHANGELOG.md` для целевой версии и закоммитить изменения. Рабочее дерево должно быть чистым.
2. Выполнить `npm run test:e2e`, если менялся интерфейс.
3. Проверить выпуск: `npm run release -- patch --dry-run` (также доступны `minor`, `major`, конкретная `X.Y.Z`).
4. Выпустить: `npm run release -- patch`. Скрипт изменяет `package.json` и lockfile, запускает сборку и тесты, создаёт коммит и аннотированный тег. При ошибке проверок коммита и тега не будет; исправить проблему, закоммитить и продолжить выпуск вручную.
5. Отправка в удалённый репозиторий выполняется отдельно. Скрипт не создаёт GitHub Release и не делает push.

Перед обновлением VPS сохранить весь том данных и текущий тег. Обновить исходники до выбранного тега и выполнить `docker compose up -d --build`. Перед возвратом к старой схеме требуется восстановить совместимую резервную копию; откат контейнера сам по себе не откатывает SQLite. Личные статьи, `.env`, ключи и БД в Git не входят.
