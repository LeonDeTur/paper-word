# Версии и Git

Единый источник версии — `package.json`. HTTP `/api/config`, MCP и настройки показывают ту же версию. Первый релиз — `0.2.0`, тег `v0.2.0`. Версия схемы SQLite — отдельное число `PRAGMA user_version` (сейчас 4); приложение отказывается открывать более новую схему. CI проверяет согласованность package-файлов и минимальной версии Node.

Ветки: `feat/название`, `fix/название`, `docs/название`, `chore/название`, `ci/название`. Коммиты и заголовки PR следуют Conventional Commits: `feat: …`, `fix: …`, `docs: …`, `chore(release): vX.Y.Z`. Префикс `codex/` не используется. Commitlint проверяет сообщения локально и в CI.

SemVer: `fix`/`perf` дают PATCH, `feat` — MINOR, `!` или `BREAKING CHANGE:` — MAJOR. В период `0.x` и новые возможности, и несовместимые изменения повышают MINOR. Несовместимость обязательно описывается в примечаниях. Технические изменения, видимые в changelog, могут войти в PATCH.

Основной путь — автоматический Release PR:

1. Слить изменения с осмысленными Conventional Commits в `main`.
2. После успешного полного CI бот создаёт/обновляет `chore/release` с версиями package-файлов, changelog и примечаниями.
3. Проверить предлагаемую версию, описание и совместимость; дождаться CI Release PR и слить его.
4. После полного CI нового `main` workflow создаст тег и GitHub Release с архивом и SHA-256. Тег относится к проверенному SHA и не переносится при повторном запуске.

Подробности и первичная настройка GitHub: [CI и релизы](ci.md).

Локальный предпросмотр: `npm run release -- --dry-run`. Для подготовки файлов вручную на чистой ветке: `npm run release` или `npm run release -- patch|minor|major|X.Y.Z`. Скрипт использует `commit-and-tag-version`, обновляет package-файлы и changelog, но **не создаёт коммит/тег и не делает push**. Затем выполните `npm run check:all`, просмотрите изменения и создайте PR с заголовком `chore(release): vX.Y.Z`. Версия должна быть выше текущей; базовый тег текущей версии должен быть доступен локально.

Не выпускайте одновременно ручной релиз и Release PR бота. Примечания формируются из коммитов; ручные заметки `[Unreleased]`, если они есть, переносятся в новый раздел. Старые разделы журнала сохраняются. Публичный runtime-архив собирается только из разрешённого списка файлов, без `.env`, БД, статей и `node_modules`.

Перед обновлением VPS сохранить весь том данных и текущий тег. Обновить исходники до выбранного тега и выполнить `docker compose up -d --build`. Перед возвратом к старой схеме требуется восстановить совместимую резервную копию; откат контейнера сам по себе не откатывает SQLite. Личные статьи, `.env`, ключи и БД в Git не входят.
